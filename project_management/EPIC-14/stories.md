### STORY-14-01 — Price Anomaly Monitor Dashboard Widget

**Status:** 🟢 Completed
**Description:** A new "Price Anomaly Monitor" section on the Dashboard lists every customer + product pair whose `unit_price` has changed by ≥ 10% (absolute value) across non-cancelled orders in the rolling past 365 days. The section is hidden from users without the `see_price_monitor` permission.

**User Perspective:**
As a Sales Manager, I want to see price anomalies on the dashboard, so that I can investigate orders where a customer received an unusually different price compared to what they were charged in the past year.

**Acceptance Criteria:**

| #     | Given                                                                                                         | When                       | Then                                                                                                                                                                          |
| ----- | ------------------------------------------------------------------------------------------------------------- | -------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| AC-01 | A user with `see_price_monitor` permission is on the Dashboard (`GET /`)                                      | The page loads             | The "Price Anomaly Monitor" section is visible with a table listing: Customer, Product (SKU + Name), First Price (YTD), Current Price, Change (%), First Order #, Latest Order # |
| AC-02 | Customer A + Product X have two non-cancelled orders within 365 days: oldest `unit_price` = 100.00, newest = 85.00 | Dashboard loads            | The widget shows 1 row for that pair with change = −15.00% (styled in red)                                                                                                    |
| AC-03 | Customer A + Product X have two non-cancelled orders within 365 days: `unit_price` changes from 100.00 to 108.00 (+8%) | Dashboard loads            | That pair is **not shown** (change < 10% threshold)                                                                                                                           |
| AC-04 | A customer + product pair has only one non-cancelled order in the 365-day window                               | Dashboard loads            | That pair is **not shown** (no comparison possible)                                                                                                                           |
| AC-05 | A user **without** `see_price_monitor` permission is on the Dashboard                                         | The page loads             | The "Price Anomaly Monitor" section is entirely absent from the rendered HTML                                                                                                 |
| AC-06 | The earliest `unit_price` for a customer + product pair in the window is `0.00`                               | Dashboard loads            | That pair is **skipped** (division-by-zero guard)                                                                                                                             |
| AC-07 | An order has `status = 'Cc'` (Cancelled)                                                                      | Dashboard loads            | Order lines from that cancelled order are **excluded** from the price monitor computation                                                                                     |
| AC-08 | No customer + product pair exceeds the 10% threshold                                                          | Dashboard loads            | The section renders with an empty-state message: "No price anomalies detected in the past 365 days."                                                                         |

**Edge Cases:**

- Customer + product pair with only one order in the rolling window → skip (no comparison possible).
- `unit_price = 0.00` on the earliest order → skip to prevent division-by-zero.
- Cancelled orders (`status = 'Cc'`) are excluded from the entire dataset.
- Widget renders empty-state message when no anomaly exceeds the threshold; the section is still visible to users with permission.
- Computation runs server-side on dashboard load; no caching in this epic (deferred to a future epic if performance warrants it).

### STORY-14-02 — Order Changes Audit Trail

**Status:** 🟢 Completed
**Description:** Every field-level change on an `Order` (status, logistic_status, address, discount, remark, etc.) and every `OrderLine` addition, removal, and quantity/price update is recorded in a new `order_audits` table, capturing the before and after values and the authenticated user responsible. The Order show page (`GET /orders/:id`) displays a chronological timeline of these records, lazy-loaded via a Turbo Frame, and gated by the `view_order_audit` permission.

**User Perspective:**
As a Sales Supervisor, I want to see a full timeline of every change made to an order and who made it, so that I can understand the complete history and hold the correct person accountable for each modification.

**Acceptance Criteria:**

| #     | Given                                                                                                             | When                                                         | Then                                                                                                                                                                                |
| ----- | ----------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| AC-01 | A logged-in user updates an Order's `status` from `Dr` to `Pd` via `PATCH /orders/:id`                           | The update saves successfully                                | One `OrderAudit` record is created: `event_type = "status_change"`, `field_name = "status"`, `previous_value = "Dr"`, `new_value = "Pd"`, `changed_by_id = current_user.id`       |
| AC-02 | A logged-in user updates an Order's `remark` field                                                                | The update saves successfully                                | One `OrderAudit` record is created: `event_type = "field_update"`, `field_name = "remark"`, `previous_value` = old text, `new_value` = new text, `changed_by_id = current_user.id`  |
| AC-03 | A logged-in user adds an `OrderLine` to an order                                                                  | The line is created and committed                            | One `OrderAudit` record is created: `event_type = "line_added"`, `new_value` = JSON string `{"product_id":N,"product_name":"...","quantity":N,"unit_price":"N.NN"}`, `changed_by_id = current_user.id` |

| AC-06 | A user with `view_order_audit` permission views `GET /orders/:id`                                                 | Page loads                                                   | A "Change History" Turbo Frame is present in the HTML; on load it requests `GET /orders/:id/audit_trail` and renders a timeline of records ordered newest-first, each showing: changer name, timestamp, event description, previous → new values |
| AC-07 | A user **without** `view_order_audit` permission views `GET /orders/:id`                                          | Page loads                                                   | The "Change History" Turbo Frame is entirely absent from the rendered HTML                                                                                                          |
| AC-08 | `Current.user` is nil during a system-triggered update (e.g. background job recalculation)                       | An audit event fires                                         | The `OrderAudit` record is created with `changed_by_id = nil`; the timeline renders "System" for that entry                                                                        |

| AC-10 | A user **without** `view_order_audit` sends `GET /orders/:id/audit_trail`                                        | Request received by `OrdersController#audit_trail`           | Response is `403 Forbidden`                                                                                                                                                         |
| AC-11 | The Admin role is seeded via `db/seeds/admin_user.rb` which assigns `Permissions::ALL` (including `view_order_audit`) | An admin user views `GET /orders/:id`                        | The "Change History" Turbo Frame is rendered and the full audit timeline is visible without requiring any manual permission grant                                                   |

**Edge Cases:**

- Fields excluded from audit tracking: `updated_at`, `updated_by_id`, `total_price`, `vat_price`, `grand_total`, `order_number`, `created_by_id`.
- `previous_value` and `new_value` strings longer than 500 characters are truncated before storage.
- `OrderAudit` records are cascade-deleted when the parent `Order` is deleted (`ON DELETE CASCADE`).
- `changed_by_id` FK uses `ON DELETE SET NULL` so that deleting a User does not erase audit history.
- The audit trail Turbo Frame uses lazy-loading (`loading="lazy"`) so it does not block the initial Order show page render.
- **Admin auto-grant:** `db/seeds/admin_user.rb` already runs `admin_role.update!(permissions: Permissions::ALL)` on every seed. No separate change to the seed file is required — adding `view_order_audit` to `Permissions::ALL` (T-14-02-08) is sufficient for the Admin role to gain access.

### STORY-14-03 — Duplicate Order Detection

**Status:** 🟢 Completed
**Description:** When an order is created or its order lines change, a Sidekiq background job evaluates whether it is a probable duplicate of another recent non-cancelled order for the same customer (at least one shared product, within a 7-day running-date window). The result is stored as a pre-computed `is_possible_duplicate` boolean column on `orders`. The Order list page renders a yellow "Possible Duplicate" badge next to the order number for flagged rows, with no impact on page load time (no extra JOIN is needed at render time).

**User Perspective:**
As an Order Manager, I want to see a visible warning when a newly created order looks like a duplicate, so that I can review it and avoid double-shipping to the same customer.

**Acceptance Criteria:**

| #     | Given                                                                                                                                                           | When                                                         | Then                                                                                                                                                               |
| ----- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| AC-01 | Order A (customer X, products [P1, P2], `running_date` = today) is created and Order B (same customer X, products [P1, P3], `running_date` = 3 days ago, `status = "Dr"`) already exists | `MarkDuplicateOrdersJob` runs for Order A                   | Order A gets `is_possible_duplicate = true` (shared product P1); Order B also gets `is_possible_duplicate = true`                                                 |
| AC-02 | Order A (customer X, products [P1]) is created and Order B (same customer X, products [P2], 3 days ago) exists — no shared products                            | `MarkDuplicateOrdersJob` runs for Order A                   | Order A gets `is_possible_duplicate = false`                                                                                                                       |
| AC-03 | Order A (customer X, products [P1]) is created and the nearest other order for the same customer has `running_date` 10 days prior                               | `MarkDuplicateOrdersJob` runs for Order A                   | Order A gets `is_possible_duplicate = false` (outside 7-day window)                                                                                               |
| AC-04 | Order A has `status = 'Cc'` (Cancelled)                                                                                                                         | `MarkDuplicateOrdersJob` runs                               | Cancelled orders are excluded from the duplicate candidate pool; the job sets `is_possible_duplicate = false` for Order A                                         |
| AC-05 | An order has no `order_lines`                                                                                                                                    | `MarkDuplicateOrdersJob` runs                               | `is_possible_duplicate` is set to `false` regardless of proximity to another order                                                                                |
| AC-06 | Order A is flagged as `is_possible_duplicate = true`; the only matching `OrderLine` product is then removed from Order A                                         | `MarkDuplicateOrdersJob` runs (triggered by `OrderLine` destroy) | Order A is re-evaluated; `is_possible_duplicate` is set to `false` if no other matching orders remain                                                             |
| AC-07 | User views `GET /orders`                                                                                                                                         | Page loads                                                   | Rows where `order.is_possible_duplicate? == true` display a yellow badge labelled "Possible Duplicate" next to the order number link                              |
| AC-08 | `GET /orders` lists 100 orders, 10 flagged                                                                                                                       | Page loads                                                   | All 10 flagged rows render the badge; no additional JOIN, sub-query, or N+1 query is introduced for the duplicate indicator (plain column read)                   |
| AC-09 | The target order is deleted between job enqueue and execution                                                                                                    | `MarkDuplicateOrdersJob#perform` runs                        | Job exits silently without raising an exception                                                                                                                    |

**Edge Cases:**

- An order is never compared to itself.
- Cancelled orders (`status = 'Cc'`) are excluded from the candidate pool as both the subject and the candidate.
- Orders with no `order_lines` are never flagged.
- The job uses `update_columns` (skipping validations and callbacks) to set `is_possible_duplicate`, preventing recursive job enqueueing.
- The job is idempotent: running it multiple times for the same order produces the same outcome.
- Clearing `is_possible_duplicate` on the subject order does not automatically re-evaluate sibling orders that may have other duplicate relationships; those are re-evaluated only when their own trigger events fire.
